# ADR-0007: Docstring conventions - heavy labeled (backend), prose JSDoc (frontend)

**Status:** Accepted
**Date:** 2026-05-02

## Context

Pre-rewrite, the codebase had no documented docstring convention. Most files had no module docstring. Models, views, serializers, permissions had auto-generated DRF/Django docstrings or none at all. Frontend components had occasional JSDoc, mostly absent.

The natural place to lock in a convention is at the start of substantial new feature work: docstrings are the cheapest pattern to apply (pure-docs, no behavior changes) and the most teaching-leveraged (every subsequent file added inherits the template). Locking in a convention before the auth rebuild and the matching/qualifier work means those features arrive with consistent shape.

The frontend's docstring needs differ from the backend's: components are typically single-purpose (no policy axes to document); module-level context dominates; per-export shape is light because TypeScript types already capture most of what JSDoc would say.

## Decision

**Two distinct docstring conventions, one per side. Backend uses a heavy labeled-section template per file kind. Frontend uses heavy module-header prose with light per-export JSDoc.**

### Backend convention

Per-file-kind templates with labeled sections. Each label is bulleted even when single-item. `"""` always on its own line; `Summary:` is the first labeled section.

| File kind | Sections |
|-----------|----------|
| Models | `Summary:`, `Business workflow:`, `Current policy:`, `Lifecycle control:`, `Visibility:` |
| Views | `Summary:`, `Flow:`, `URL:`, `Methods:` (multi-method only), `Auth:`, `Errors:` |
| Permissions | Class: `Policy:`, `Used by:`. Methods: `Branches:`. |
| Serializers | One-liner + optional prose + `Used by:` |
| URL configs / scaffold / tests | Light prose-only module docstring |

Vocabulary tags lock in for `Lifecycle control:` (`admin-managed`, `user-managed`, `creator-managed`, `pd-synced`) and `Visibility:` (`public-read`, `auth-required`, `internal`, `pm-write`, `creator-write`, `pm-delete`). Stage qualifiers compose: `admin-managed (Stage 1) -> pd-synced (Stage 2)`.

Single backticks for code refs (greppable). 88-char line limit (matches ruff format default).

The full templates with examples live in [`docs/developer/backend-docstring-style.md`](../developer/backend-docstring-style.md).

### Frontend convention

Heavy module headers, light per-export. The file is the unit of design on the frontend; the file-header is where context goes.

- **Module header**: 1-2 sentence summary + 1-3 short paragraphs (what the file does, what it exports in user-facing terms, non-obvious decisions).
- **Per-export JSDoc**: one-liner unless the export has non-obvious behavior. Don't redocument what TypeScript types already capture.
- **Prose-style, not labeled-section**: components and utilities usually have a single purpose; there's nothing to label.

Per-kind variants for app routes, feature components, shared UI primitives, utilities, contexts, static data, type declarations, and tests live in [`docs/developer/frontend-docstring-style.md`](../developer/frontend-docstring-style.md).

### Bug-flagging

When a docstring sweep surfaces a bug, the bug is flagged inline in the docstring (not silently fixed). The flag travels with upstream history. Flags are written as a paragraph in the docstring's prose, not as a labeled section, because they're transient (each will be resolved in a future PR).

## Alternatives considered

- **Free-form prose paragraphs.** Section ordering varies per author; a reviewer scanning the file can't predict where to look for the policy or the URL. Not scannable. Rejected.

- **Sphinx/RST docstring format.** Discarded because the project uses Markdown for docs, not RST; Sphinx's `:param:` / `:returns:` shape duplicates what type hints already say; the project doesn't have an autogenerated-API-docs workflow that would pay off the RST tax.

- **Google-style or Numpy-style docstrings.** Discarded because both are designed around `Args:` / `Returns:` blocks that mirror function signatures. Most CTJ symbols are classes (Models, Views, Serializers, Permissions) where the interesting documentation isn't argument-shaped.

- **One unified convention across backend and frontend.** Discarded because the backend's policy axes (Lifecycle, Visibility, Auth, Errors) don't map to frontend components, and frontend's "what does this whole file do" framing doesn't map to backend's per-class policy.

- **Skip the convention; let docstrings stay ad-hoc.** Discarded because the modernization-tip codebase was about to grow significantly. Locking in a shape before that work lands means the new files arrive consistent.

## Consequences

**Accepted:**

- Future contributors must follow the convention or have it pointed out in review. Mitigated by the per-side style guides being authoritative references; PR review is the enforcement layer.

- The vocabulary tags are project-specific. New contributors learn them from the docstring style guide; PR review reinforces.

- Single-backtick refs aren't enforced by tooling (no docstring linter); RST double-backticks could leak in. Mitigated by the style guide being explicit and PR review catching.

**Won:**

- Reading `models.py` cold answers "what controls each row's lifecycle, who can see it, who can write it" without leaving the file. The labeled sections create a scan path.

- Future feature work starts with a docstring template; new files arrive in the conventional shape rather than being retrofit.

- Per-kind variants mean the template fits each file's natural shape - models get heavy policy detail, serializers get a one-liner + Used by:, tests get behavioral docstrings.

- The frontend's "module header is heavy, per-export is light" matches how frontend files are actually read (file-as-unit-of-design); the backend's "every class has labeled policy" matches how backend classes are actually read (per-class policy as the unit).
