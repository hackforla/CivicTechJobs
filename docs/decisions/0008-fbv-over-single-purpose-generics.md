# ADR-0008: FBVs over single-purpose DRF generics and ReadOnlyModelViewSets

**Status:** Accepted
**Date:** 2026-05-02

## Context

DRF gives several ways to write a view: `ModelViewSet` for full CRUD, `ReadOnlyModelViewSet` for list+retrieve, single-purpose generics like `RetrieveAPIView`, and function-based views (FBVs) decorated with `@api_view`. Each hides different amounts of behavior.

`ReadOnlyModelViewSet` resolves to "list + retrieve" only if you know DRF; nothing in the class body says so. `RetrieveAPIView` resolves to "GET single record" only if you know DRF. Routes are auto-generated by `DefaultRouter` from class names, so nothing in `views.py` tells you what URL the view answers on. Reading `views.py` cold, you can't answer "what methods does this view expose?" or "what URL serves it?" without cross-referencing DRF source and `urls.py`.

This project is read by volunteers with varying DRF familiarity; explicit beats clever.

## Decision

**Convert both single-purpose generics and `ReadOnlyModelViewSet`s to function-based views (FBVs). Keep `ModelViewSet` only for resources that genuinely span the full CRUD surface (≥4 of list/create/retrieve/update/destroy).**

The rule:

| Endpoint shape | View shape |
|----------------|------------|
| Full CRUD on a resource (≥4 of list/create/retrieve/update/destroy) | `ModelViewSet` registered on `DefaultRouter` |
| Anything narrower - single method, list-only, retrieve-only, list-and-retrieve, custom action | FBV decorated with `@api_view([...])` and explicit `permission_classes` |
| Non-resource (health, fallbacks, RPC-style operations) | Plain Django `def view(request)` |

`ReadOnlyModelViewSet`s become FBV pairs (one for list, one for retrieve), explicitly routed in `urls.py`. The router only carries `ModelViewSet`s.

## Alternatives considered

- **Keep all CBV/generic shapes (status quo).** Less code, idiomatic DRF. Discarded because the cost is paid every time someone reads `views.py` cold - DRF's "convention over configuration" hides the conventions in framework source. The "less code" win is small in absolute terms (~30 lines net for converting 4 viewsets to 8 FBVs).

- **Strict reading of "single-purpose": only convert single-method generics, keep all `ReadOnlyModelViewSet`s.** Discarded because it leaves the codebase with three view shapes - `ModelViewSet` for full CRUD, `ReadOnlyModelViewSet` for list-and-retrieve, FBV for everything else. Two shapes (full-CRUD-ViewSet vs FBV) is easier to teach and audit.

- **Convert everything to FBVs, including full-CRUD resources.** Maximum explicitness; every method, route, permission visible inline. Discarded because `ModelViewSet`'s value-add is real when you actually use the full CRUD surface - `perform_create`, `get_queryset`, automatic `OPTIONS` handling. Re-implementing that across 6 FBVs for a resource that needs all 6 is cargo-cult explicitness.

- **Keep generics, add explicit `http_method_names` and route declarations as docstring-only metadata.** Discarded because docstrings can drift from the actual class behavior. The information needs to be in the code, not in prose around it.

## Consequences

**Accepted:**

- `urls.py` grows. Each `ReadOnlyModelViewSet` previously took one line (`router.register(...)`); the FBV pair takes two `path()` entries.

- FBVs lose `DefaultRouter`'s auto-generated `OPTIONS` handling. Mitigated by Django's `APPEND_SLASH` middleware and by being explicit about which methods each FBV accepts.

- Custom actions (`@action(detail=True)` on a viewset) need a different idiom in FBV land - typically a separate FBV with its own URL.

- DRF's browsable API still renders FBVs, but the "available actions" list per resource looks slightly different from the viewset shape. Acceptable; the browsable API is a developer convenience, not a contract.

- `has_object_permission` (object-level permission classes) is auto-triggered by generic-view internals but **not** by `@api_view`. An FBV that uses a permission class with object-level checks needs to call `request.parser_context["view"].check_object_permissions(request, obj)` explicitly after the object lookup. The pattern is documented in [`docs/developer/backend.md`](../developer/backend.md)'s `View shape` section.

**Won:**

- Reading `views.py` answers "what methods does this view support?" and "what URL does it serve?" without leaving the file. The `@api_view(["GET"])` decorator is right above the function; the URL is a `grep` away in `urls.py`.

- Two view shapes instead of three. Reviewers and new contributors learn one rule (full CRUD ⇒ ViewSet, otherwise FBV) instead of three.

- The "≥4 of full CRUD" rule for ViewSets is auditable at PR-review time. A reviewer can ask "does this new view need all of list/create/retrieve/update/destroy?" - if not, it's an FBV, no debate.

- `urls.py` growth is itself an explicitness win: every route is now visible at the routing layer rather than synthesized at startup. `grep "/api/skills"` lands you on a real line.
